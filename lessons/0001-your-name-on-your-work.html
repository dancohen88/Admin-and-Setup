GitHub / Lesson 01

Your Name on Your Work

There is already a repository of yours on GitHub. You didn’t put it there, and right now it doesn’t have your name on it. By the end of this page it will — and you’ll understand exactly why it didn’t.

12 minutes git identity GitHub auth

The situation

Your mission is to publish your own projects and have that work be visibly, permanently yours. So let’s check whether it currently is.

The folder you’re sitting in is a git repository with one commit in it, and that commit has already been sent to GitHub, at dancohen88/Admin-and-Setup. A previous session did that for you — which means you have never actually run the commands yourself. That’s what we’re fixing.

Here’s the problem. Ask GitHub who wrote that commit:

zsh
# Who does GitHub think wrote your one commit?
$ curl -s https://api.github.com/repos/dancohen88/Admin-and-Setup/commits/e0c3903 \
    | grep -m1 '"login"' || echo 'no GitHub account matched'

It prints no GitHub account matched. GitHub has the commit, but it cannot tell that you made it. On the website that commit shows a grey silhouette instead of your avatar, and it earns you no square on your contribution graph.

To see why, ask git what it stamped on the commit:

zsh
$ git log -1 --format='%an <%ae>'

Daniel Cohen <danielcohen@Daniels-MacBook-Pro.local>

That email address does not exist. Nobody can receive mail at it. It is your laptop’s internal network name, which git invented because you never told it who you are.

The exact failure, documented

GitHub’s troubleshooting page lists the conditions for a commit to count, and names this precise case: contributions must be “authored using a valid email address” — explicitly not generic addresses like jane@computer.local.

Yours is danielcohen@Daniels-MacBook-Pro.local. Same shape, same result.

GitHub Docs — Why are my contributions not showing up on my profile?

The one idea

Almost every beginner confusion with GitHub dissolves once you separate two things that feel like one thing.

Identity

git · on your Mac

  • Who a commit says wrote it
  • Stamped in by git, offline
  • Set with git config user.email
  • Permanent once the commit exists

Authentication

GitHub · over the network

  • Who is allowed to upload it
  • Checked by GitHub, at push time
  • Set with gh auth login
  • Changeable any time

Your repo has neither configured. It reached GitHub anyway because a previous session supplied its own credentials — but the identity stamped on the commit was never yours to begin with.

Why this matters later

The two systems never consult each other. That’s why a commit can carry your name and still be rejected on push, and why a commit you did push can still show up as someone else.

And here is the part you can’t undo later. Pro Git — the canonical git book, written by a GitHub co-founder — puts it plainly:

Pro Git §1.6 — First-Time Git Setup

Your identity is important because “every Git commit uses this information, and it’s immutably baked into the commits you start creating.”

Pro Git, 2nd ed. — Getting Started: First-Time Git Setup

Immutably baked. Commit e0c3903 will carry that dead address for as long as the repo exists. We are not going to fix it — rewriting history is a later, sharper tool, and it isn’t worth it for one commit. We’ll set your identity correctly and leave that commit as a fossil of what happens when you don’t.

GitHub decides whose avatar to show beside a commit. What does it match on?

Email, and only email. The author name is free text GitHub never checks — you could commit as “Ada Lovelace” and it wouldn’t blink. The account that pushed is a separate question entirely: that’s authentication, not identity. Your one commit already proves it, since it was pushed successfully but attributed to nobody.

Do it

  1. Tell git who you are

    Your name is free text — use whatever you want shown. Your email is the part that has to be exact.

    zsh
    $ git config --global user.name "Daniel Cohen"
$ git config --global user.email "321021787+dancohen88@users.noreply.github.com"

    --global means “for every repo on this Mac,” so this is a once-per-machine job, not once-per-project.

    That second address isn’t one I invented — GitHub issued it to you. It’s your account’s noreply address, in the documented form ID+username@users.noreply.github.com, where 321021787 is your account’s permanent numeric ID.

    Using it rather than your real inbox buys two things: your actual email never appears in a public commit where scrapers can harvest it, and because the ID never changes, attribution survives even if you rename your account later — which the older username-only form does not.

    GitHub Docs — Email addresses reference

  2. Prove it took

    zsh
    $ git config --global --get user.name
$ git config --global --get user.email

    Each should echo back what you just set. If either prints nothing, the command didn’t land — check for a typo and run it again.

  3. Log in to GitHub

    Now the other half: authentication. gh is already installed on your Mac but has never been logged in.

    zsh
    $ gh auth login

    Answer the prompts: GitHub.com → HTTPS → Yes (authenticate git with your GitHub credentials) → Login with a web browser. It shows an eight-character code, opens your browser, you paste the code, done.

    Saying yes to “authenticate git” is what lets plain git push work afterwards without asking for a password every time. Confirm it worked:

    zsh
    $ gh auth status

✓ Logged in to github.com account dancohen88

  4. Make a commit that’s actually yours

    We need something real to commit, and there’s a genuine error sitting in your repo: README.md claims the project is “ready to be published to GitHub.” It was published hours ago. Let’s make it true.

    Open README.md and replace its contents:

    # Admin and Setup

My workspace for learning Git and GitHub.

Published at https://github.com/dancohen88/Admin-and-Setup

    Then run the three commands that turn an edit into published work:

    zsh
    $ git add README.md
$ git commit -m "Update README to reflect published state"
$ git push

    add chooses what goes in. commit takes the snapshot, locally. push sends it to GitHub. Three separate acts — the subject of lesson 02.

    The commit step is where your new identity gets stamped on. The push step is where your new login gets used. This one sequence exercises both halves of the split above.

  5. Collect the win

    Ask GitHub the same question we opened with, this time about your new commit:

    zsh
    $ gh api repos/dancohen88/Admin-and-Setup/commits/$(git rev-parse HEAD) \
    --jq '.author.login'

dancohen88

    Where the first commit returned nothing, this one returns you. Now look at it:

    zsh
    $ gh repo view --web

    Your browser opens the repo. Your new README is on the front page, and beside your commit is your username and your avatar. The commit above it still shows a grey silhouette — the fossil, exactly as predicted.

What you just did

You configured a permanent machine-wide git identity, authenticated a real GitHub session, and ran the full add → commit → push loop under your own name. Every commit you make on this Mac from now on — in this repo or any other — will be correctly attributed to you, without you thinking about it again.

You edit a file and run git commit. Where does that change exist?

Committing is a purely local act — git works with your Wi-Fi off. Nothing reaches GitHub until git push. This is the distinction that catches nearly every beginner: they commit carefully all week, never push, and lose it all with the laptop. A commit is a save. A push is a backup.
