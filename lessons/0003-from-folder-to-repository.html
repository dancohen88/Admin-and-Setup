GitHub / Lesson 03

From Folder to Repository

There is a finished game on your laptop called Mosslight Hollow. Nobody can see it, nothing is backing it up, and it has never been anywhere near git. By the end of this page it will have a URL.

14 minutes git init gh repo create

The situation

Your mission opens with a complaint about your own hard drive: work sits in local folders that nobody else can see and no backup protects. That is still true. Here is the evidence:

zsh
$ ls ~/Sandbox

0x72_DungeonTilesetII_v1.7
Admin and Setup
Archer.png
Cosy Crawler 2
Cosy Dungeon Crawler
Warrior.png
Wizard.png
family
family-planner

Two of those are on GitHub — Admin and Setup and family. The three project folders that aren’t (Cosy Crawler 2, Cosy Dungeon Crawler, family-planner) are one spilled coffee from never having existed. We’re going to fix the best of them.

Cosy Dungeon Crawler is 27 files and 244 KB — a complete top-down dungeon crawler in vanilla JavaScript, with tests, a plan, and a style guide. It has zero installed dependencies. And it is not a git repository:

zsh
$ ls -a ~/Sandbox/"Cosy Dungeon Crawler"

.          PLAN.md     package.json  styles.css
..         STYLE.md    public        test
CLAUDE.md  index.html  server.js

No .git in that list. No history, no commits, no remote — nothing to push even if you wanted to. This is genuinely new ground: every repository you have touched so far already existed before you got there. This one you make.

The one idea

Publishing a folder that already exists is not one act. It is two separate creations, in a specific order, and then a single link between them.

1. The local repo

git init · on your Mac

  • Creates the .git folder
  • Instant, offline, free
  • Tracks nothing yet
  • Where you commit

2. The GitHub repo

gh repo create · on the web

  • Creates the page and URL
  • Needs the network
  • Public or private, your call
  • Where you push

Order matters. Make the local repo first and commit into it, then create the GitHub one from it. That way GitHub’s copy is a copy of something real, and the connection between the two gets set up for you in the same breath.

Do it the other way round — empty repo on the website first, then try to marry it to a folder afterwards — and you spend your afternoon reading Stack Overflow answers about unrelated histories. That route exists and has its uses. It is not the one for today.

What git init actually does

It makes one hidden folder, .git, and puts an empty history in it. That is all. Your 27 files are not touched, not copied, and not tracked — they are sitting in exactly the ?? state you met in lesson 02.

Which is why git will call your full, finished game an empty repository and be completely correct.

You run git init in a folder holding 27 files. What is now tracked?

init creates the repository; it does not fill it. Every one of those 27 files is untracked until you git add it — the same first heading git status showed you last lesson. Making a repo and putting something in it are two different jobs.

Do it

  1. Fix the default branch name, once

    Before you init anything. Left alone, git 2.50 still names the first branch master and prints a paragraph of apology about it every single time:

    zsh
    $ git config --global init.defaultBranch main

    GitHub uses main. Your other repo uses main. Every current tutorial uses main. This is a once-per-machine setting like your identity in lesson 01 — set it and never think about it again.

  2. Turn the folder into a repository

    zsh
    $ cd ~/Sandbox/"Cosy Dungeon Crawler"
$ git init

Initialized empty Git repository in
/Users/danielcohen/Sandbox/Cosy Dungeon Crawler/.git/

    The quotes around the folder name matter — without them the shell reads Cosy, Dungeon and Crawler as three separate arguments. Typing cd ~/Sandbox/Cosy and hitting Tab lets the shell do the quoting for you.

    “Empty,” it says, standing in a folder with a whole game in it. Look:

    zsh
    $ git status --short

?? CLAUDE.md
?? PLAN.md
?? STYLE.md
?? index.html
?? package.json
?? public/
?? server.js
?? styles.css
?? test/

    Nine lines of ??, folders collapsed, exactly as last lesson taught you to read it. The repo exists and holds nothing.

  3. Give it a front page

    There is no README.md in that list, and GitHub renders README.md as a repo’s front page. Without one, the first thing a visitor sees is a bare file listing.

    Your package.json already describes the project better than the folder name does — it calls it mosslight-hollow, “a cozy top-down lo-fi dungeon crawler, built with vanilla HTML/CSS/JS Canvas.” Use its own words. Create README.md:

    # Mosslight Hollow

A cozy top-down lo-fi dungeon crawler, built with vanilla HTML/CSS/JS Canvas.
No dependencies — Node 18+ is the only requirement.

## Running it

    npm start

Then open http://localhost:3000

    That is a placeholder, not a good README — lesson 06 is about writing one that actually earns a stranger’s attention. It beats an empty front page today.

  4. Make the first commit

    Lesson 02 told you to be wary of git add . Here it is the right call, and the wariness is what makes it so: you have already run git status --short and seen all nine entries. There is no node_modules to sweep up, because this project installs nothing. Everything in the folder genuinely belongs in the repo.

    zsh
    $ git add .
$ git status --short
$ git commit -m "Initial commit: Mosslight Hollow, a cozy dungeon crawler"

    Check the middle command before you run the third — every line should have flipped from ?? to A, and README.md should now be among them.

  5. Choose the name, then create it on GitHub

    This is the one irreversible-ish decision on the page, so take it deliberately. The repository name becomes a URL: github.com/dancohen88/<name>. Renaming later works, but every link anyone has saved breaks.

    gh defaults to the folder name, which would give you Cosy-Dungeon-Crawler — spaces silently turned into dashes. Your project calls itself something better:

    zsh
    $ gh repo create mosslight-hollow --source=. --public --push \
    --description "A cozy top-down lo-fi dungeon crawler in vanilla JS"

✓ Created repository dancohen88/mosslight-hollow on GitHub
✓ Added remote https://github.com/dancohen88/mosslight-hollow.git
✓ Pushed commits to https://github.com/dancohen88/mosslight-hollow.git

    Four flags, each doing one thing:

    FlagWhat it does
    --source=.Build the repo from this folder. Without it you get an empty repo unconnected to anything.
    --publicAnyone can read it. One of --public or --private is required — there is no default, on purpose.
    --pushSend the commits now, and wire up origin so plain git push works from here on.
    --descriptionThe one-line blurb under the repo name. Optional, and the difference between a project and a folder.

    Public is right for this one: it is a game, it holds no secrets, and public repos are what show up on your profile. When you are unsure, use --private — lesson 07 covers switching, and switching to private after the fact is the switch that doesn’t fully work.

    GitHub Docs — Adding locally hosted code to GitHub

  6. Confirm all three parts landed

    Three things had to happen. Check each rather than trusting the ticks:

    zsh
    # is there a remote, and does it point at the right place?
$ git remote -v

# is the local branch paired with GitHub's, and in sync?
$ git status -sb

## main...origin/main

    No ahead and no behind on that last line means both copies hold identical history. Then look at the thing itself:

    zsh
    $ gh repo view --web

    Your README on the front page, your description under the title, your avatar beside the commit — that last part courtesy of the identity you set in lesson 01, working automatically in a repository that did not exist when you set it.

What you just did

You published a project from scratch: init, a first commit, a named repo, and a push, in about five commands. That is the first line of your mission’s success list, and you can now do it to anything on your laptop.

The trap waiting for you

git add . was safe here because Mosslight Hollow installs nothing. The day you run npm install on a project with real dependencies, a node_modules folder appears containing tens of thousands of files, and git add . will take every one of them.

The fix is a .gitignore, and it is lesson 05. Until then, run git status --short before you add, and notice if the list suddenly gets long.

gh reported “Added remote”. What is a remote?

A nickname and a URL, nothing more: origin now means https://github.com/dancohen88/mosslight-hollow.git. Having a remote moves no data whatsoever — --push is what sent your commit. This matters more than it sounds: git never syncs behind your back. A repo can have a perfectly good remote and be months out of date, which is exactly how people lose work they thought was backed up.

Where this goes

Two more are still sitting there. family-planner is already a git repo with a .gitignore and commits in it — so publishing it is only steps 5 and 6 of this page, and it is worth doing on your own to prove the sequence stuck. Cosy Crawler 2 is stranger: a .git folder with nothing beside it. Ask me about that one.

Lesson 04 is undoing. You can now put work on the internet quickly, which means you can now put a mistake on the internet quickly — a wrong file, a bad edit, a commit you regret. The next lesson is how to walk each of those back, and which of them can’t be.

Ask me anything about this. If gh repo create refused, if the name was taken, if the push asked for a password, if you picked a different name and want to change it — say so. Renaming a repo you published ten minutes ago is easy; the whole point of doing it now is that nothing has linked to it yet.

Two worth asking: “What actually is in the .git folder?” and “How do I get this onto a second computer?”
