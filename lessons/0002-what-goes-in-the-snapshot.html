GitHub / Lesson 02

What Goes in the Snapshot

Your most recent commit says it updated the README. It never touched the README — it added MISSION.md. That isn’t git misbehaving. It’s git doing exactly what you asked, and the gap between those two things is this entire lesson.

13 minutes git status the staging area

The situation

Since lesson 01 you’ve run the add → commit → push loop under your own name, twice, unaided. That’s the part that matters and it worked. But look at what the second one actually contains:

zsh
$ git log -1 --stat

    Update README to reflect published state

 MISSION.md | 31 +++++++++++++++++++++++++++++++
 1 file changed, 31 insertions(+)

The message promises a README update. The contents are MISSION.md. The README is not in there at all — and that commit is already on GitHub, where the message is the only thing most people will ever read.

You didn’t do anything careless. You hit the exact trap this lesson exists to remove: your first git add README.md reported nothing added to commit, because the file hadn’t been changed yet. By the time a commit succeeded, what was in it was a different file — and the message you’d written for the first attempt came along with it.

Why the first attempt did nothing

Naming a file in git add does not mean “include this file.” It means “take the changes currently sitting in this file.” An unedited file contains no changes, so git add picked up nothing, and git commit had nothing to record.

git does not store files. It stores differences you have chosen.

We’re leaving 1845eb6 as it is — it’s pushed, and rewriting published history is a sharp tool for much later. The repair isn’t to that commit. It’s that every commit after it says what it holds.

And there is plenty waiting. Ask the repo what state it’s in:

zsh
$ git status

On branch main
Your branch is up to date with 'origin/main'.

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	NOTES.md
	RESOURCES.md
	assets/
	learning-records/
	lessons/
	reference/

nothing added to commit but untracked files present

Every page of this course is sitting in that list, on one laptop, backed up by nothing. By the end of the page it’ll be on GitHub — in two commits that each tell the truth.

The one idea

A change you make has to travel through three places before it’s safe. Almost every confusing thing git says is really just telling you which of the three something is in.

Working directory

on disk

  • Every edit you save
  • git can see it
  • Not in the next commit
  • Gone if you delete it

Staging area

the box

  • What add puts in
  • Nothing sealed yet
  • Is the next commit
  • You can take it out

Commit

sealed

  • What commit seals
  • Permanent and named
  • Still only on your Mac
  • Needs push to leave

All three are amber — all three are git, on your machine, with the Wi-Fi off. GitHub doesn’t appear until push, which you already know how to do.

The middle one is the part nobody explains. The staging area is a box you put changes into. git add puts a change in; git commit seals whatever is in the box and labels it. Nothing else goes in that snapshot, no matter what else you’ve been editing.

Which makes git status readable. It isn’t one list — it’s up to three, and the heading over each one tells you where those changes are:

What status calls itWhat that meansIn the next commit?
Untracked filesgit has never recorded this file, everNo
Changes not staged for commitYou edited a file git already knowsNo
Changes to be committedChanges you put in the boxYes

Right now your repo shows only the first heading, which is why it looks so empty. Nothing is in the box yet.

Why the box exists at all

It looks like a pointless extra step until the first morning you fix a bug and rewrite a paragraph and rename a file, all before lunch. Those are three unrelated things, and a history that records them as one lump is a history nobody can read or undo selectively.

The box lets you take one pile of edits and ship it as several honest commits. That is the entire reason it is there.

You edit three files, then run git add notes.md and commit. What does that commit hold?

Only what you put in the box. The other two files keep their edits — they’re still sitting in your working directory, perfectly safe, just not in this snapshot. And note the last option: push only sends commits that already exist. It never creates one.

Do it

Six untracked entries, two different ideas: the lesson pages themselves, and the notes about the course. So — two commits.

  1. Read the status as lists, not as noise

    Run it again, and this time read the heading rather than the filenames:

    zsh
    $ git status --short

?? NOTES.md
?? RESOURCES.md
?? assets/
?? learning-records/
?? lessons/
?? reference/

    --short is the form you’ll actually live in. ?? means untracked — git has never seen this and won’t touch it until told.

    Four of those six are folders. git never tracks a folder, only files, so when nothing inside one is tracked it collapses the whole thing to one line rather than listing twenty files you haven’t asked about yet.

  2. Put the first group in the box

    zsh
    $ git add lessons reference assets

    Nothing printed. That’s normal — git commands that succeed are usually silent. Don’t take the silence on trust; look in the box:

    zsh
    $ git status --short

A  assets/artifact-urls.json
A  assets/build-artifact.py
A  assets/copy-button.js
A  assets/course.css
A  assets/quiz.js
A  lessons/0001-your-name-on-your-work.html
A  lessons/0002-what-goes-in-the-snapshot.html
A  reference/0001-glossary.html
?? NOTES.md
?? RESOURCES.md
?? learning-records/

    Eight entries flipped from ?? to A — added, in the box. The three you didn’t name stayed exactly where they were. Naming a folder staged the files inside it, which is the one shortcut worth having.

    The page you are reading is on that list.

  3. Know what git add . really does

    You will see git add . in every tutorial on the internet. It means “everything in this folder, whatever it happens to be.” It works, and it is how people accidentally publish a 400 MB video, a folder of holiday photos, or a file with a password in it.

    The habit worth building now

    Name what you mean, or run git status first and know what . is about to sweep up. Not because git add . is wrong — because a public repo remembers everything, and “I’ll delete it later” doesn’t work once it’s pushed.

  4. Seal it with a message that’s true

    Write the message after looking in the box, describing what’s in it:

    zsh
    $ git commit -m "Add lesson 01, the glossary, and the shared stylesheet"

[main 3f2a1c9] Add lesson 01, the glossary, and the shared stylesheet
 8 files changed, 1204 insertions(+)

    Your hash and line count will differ — the shape is what matters. Now ask the same question we opened the lesson with:

    zsh
    $ git log -1 --stat

    This time the message and the file list agree. That’s the whole repair: not clever commands, just looking in the box before you seal it.

    A message that works: one line, present tense, says what the change does. If you can’t say it in one line, that’s not a writing problem — there are two commits in your box.

  5. Do the second one yourself

    Same three moves, no hand-holding: stage the notes, check the box, seal it.

    zsh
    $ git add NOTES.md RESOURCES.md learning-records
$ git status --short
$ git commit -m "Add course notes, resources, and learning records"

    learning-records/ is my running notes on how you are getting on. If you’d rather that wasn’t on the public internet, leave it out — stage NOTES.md RESOURCES.md only, and shorten the message to match. Keeping files out permanently is .gitignore, later in the course.

  6. Send them

    zsh
    $ git push
$ git log --oneline -3

    One push, two commits. Push moves everything you’ve committed since last time — it isn’t per-commit, and you don’t have to do it after every single one.

    zsh
    $ gh repo view --web

    The course is on the front page of your repo, in two commits whose messages describe them — sitting directly above one that doesn’t.

The gotcha this creates

The box holds a copy, taken the moment you ran git add. Stage a file, edit it again, and git status shows that one file in both lists at once — the staged version and the newer unstaged one. Nothing is broken; it’s the clearest proof the box is a real, separate place.

The fix is to git add it again, which replaces what’s in the box.

What you just did

You took one pile of unrelated work, split it deliberately into two commits, checked the contents of each before sealing it, and pushed both in one go. That’s not a beginner workflow you’ll grow out of — that’s the loop, and it doesn’t change when the repo gets bigger.

git status lists one file as both staged and not staged. Why?

Staging copies the change as it looked at that moment. Editing afterwards creates a second, newer change that isn’t in the box — so git honestly reports both. Commit now and you get the older version. git add it again and the box catches up.

Where this goes

You can now put work into a repo that already exists. The mission is to publish work that doesn’t — and that’s lesson 03: taking an empty folder with nothing in it and having it live on GitHub, under your name, in a couple of minutes. Every step of it is a command you already know except the first one.

Still deliberately unresolved: e0c3903 has nobody’s name on it, and 1845eb6 has a message that lies. Both are fixable. Both are history rewriting, and that comes after you’ve learned to undo things that haven’t been published.

Ask me anything about this. Especially here — the staging area is the single most common place beginners quietly give up and start copying commands. If a git status came back looking different to the page, paste it at me. That’s the fastest thing you can do.

Two worth asking now: “How do I take something back out of the box?” and “What if I commit with a message I immediately regret?”
