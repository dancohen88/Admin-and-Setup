Git & GitHub Glossary

The vocabulary, in the order it starts to matter. Every lesson in this course uses these words to mean exactly these things.

Living document git — the tool GitHub — the website
How to read the tags

Two different products share this vocabulary, and confusing them is the single most common source of beginner frustration. Each term is tagged with which one owns it: git for the program on your Mac, github for the website.

The two systems

git git
A program on your computer that records snapshots of a folder over time. Completely offline. It has nothing to do with GitHub, works fine with no internet connection, and predates GitHub by three years.
GitHub github
A website that stores copies of git repositories and adds a social layer — profiles, issues, pull requests. One of several such sites; GitLab and Codeberg are others. git is the tool, GitHub is a place to put the results.
pager less
Deliberately untagged: a pager belongs to neither system. It is a separate program — usually one called less — that your terminal hands long output to so you can scroll it. git passes anything taller than your window to it, which is why a finished git log can look like a frozen terminal: the pager has taken the keyboard and is waiting. (END) means you have reached the bottom. Press q to get out. space pages down, b pages back, /word searches. To stop git using one at all: git config --global core.pager cat.

Things that hold your work

repository repo git
A folder git is tracking, plus the hidden .git subfolder holding its entire history. Delete .git and you have an ordinary folder again, with every version but the current one gone.
git init git
The command that turns an ordinary folder into a repository, by creating the .git subfolder with an empty history in it. It touches none of your existing files and tracks none of them — a freshly initialised folder of finished work is still, correctly, an empty repository. Run once per project, ever.
working directory working tree git
The files as they exist right now, the ones you can open and edit. The only part of a repo you see in Finder.
staging area the index git
A holding pen between your edits and a commit. You git add files into it to say “these changes belong in the next snapshot.” It exists so one commit can contain some of your changes rather than all of them.
commit git
A permanent, timestamped snapshot of the staged files, plus a message saying why. Commits are the unit of history. Each records an author name and email baked in at creation, which cannot be edited afterwards without rewriting history.
commit hash SHA git
The 40-character fingerprint identifying a commit, e.g. e0c39031f08d…, usually shortened to the first seven (e0c3903). Two repos holding the same hash hold byte-identical history — which is how you prove a push worked.

The states of a change

tracked git
A file git has recorded at least once, and is therefore watching for changes. Tracking is per-file and permanent until you deliberately remove it.
untracked git
A file git can see but has never recorded. It is never included in a commit and never altered by git. New files start here; git add is what moves them out. In git status --short these are marked ??.
modified git
A tracked file whose contents on disk no longer match the last commit. Being modified is not enough to get into a commit — the change still has to be staged.
staged to stage git
A change that has been put into the staging area and will be in the next commit. Staging takes a copy of the change as it was at that moment: edit the file again and the same file appears as both staged and modified, which is git being accurate rather than broken.
git add git
The command that stages changes. Despite taking filenames, it does not operate on files — it takes whatever differences those files currently hold. Running it on an unchanged file does nothing at all. git add . stages everything in the folder, including things you may not have meant.
git status git
The command that reports which of the three states every change is in, under a heading per state. Read the headings, not the filenames. --short gives the compact daily form.
diff git
The set of lines added and removed between two versions — the actual unit git stores. git diff shows changes you have not staged; git diff --staged shows what is in the box, waiting.
commit message git
The one-line description sealed into a commit alongside the changes. Written with -m. Nothing checks that it is true of the contents, which is why it can be — and on a public repo, it is the only part most readers ever see.

Where work lives

local git
On your machine. Your commits are local until you deliberately send them elsewhere.
remote git
A nickname for a copy of the repo that lives somewhere else, stored as a URL. A repo can have several. Having a remote configured does not mean anything has been sent to it — it only records the address.
origin git
The conventional name for the primary remote. Not a keyword — just a habit so universal that tools assume it. origin is to remotes what main is to branches.
branch git
A movable label pointing at a commit, marking one line of development. Work on a branch doesn’t affect other branches until merged.
main git
The conventional name for the default branch — the authoritative version of the project. Older repos and tutorials call it master.
init.defaultBranch git
The setting that decides what git init names your first branch. Unset, git still picks master and prints a hint about it every time. Set it once with git config --global init.defaultBranch main to match GitHub and everything else.
HEAD git
A pointer to where you are right now, normally the newest commit on your current branch. When git says “HEAD,” read it as “the commit you’re standing on.”

Moving work between them

push git
Send local commits to a remote. This is the step that puts your work on the internet; committing alone never does.
pull git
Fetch commits from a remote and merge them into your local branch. The reverse of push.
clone git
Download a complete repo — every commit, not just the current files — and set up origin pointing back where it came from. How you get an existing project onto a new machine.
gh repo create github
Creates the repository on GitHub. With --source=. it builds it from a local repo you already have, adds origin, and with --push sends your commits and sets up the tracking branch in one go. Requires --public or --private explicitly — there is deliberately no default.
tracking branch upstream git
A local branch paired with a remote branch, so bare git push and git pull know where to go. Set once with git push -u origin main; the -u is what creates the pairing.

Identity and credit

author identity git
The user.name and user.email stamped into every commit you make. Set once with git config --global. If unset, git invents an address from your computer’s hostname — which belongs to nobody.
attribution github
GitHub matching a commit’s author email to a registered account, then showing that account’s name and avatar beside the commit. Matching is by email only; the name in the commit is ignored. No match, no attribution.
contribution graph github
The grid of green squares on a GitHub profile. A commit only earns a square if its email is connected to the account, it’s on the default branch, and the repo isn’t a fork.
noreply address github
A GitHub-issued email of the form ID+username@users.noreply.github.com that identifies you for attribution without exposing a real inbox. Safe in public commits. The numeric ID keeps working even if you change your username.
authentication github
Proving to GitHub that you may write to a repo — separate from identity. Identity is who a commit says wrote it; authentication is who is allowed to push it. A commit can carry your name and still be rejected, and vice versa.
gh GitHub CLI github
GitHub’s official terminal program. Handles the website’s features — creating repos, logging in, opening pull requests — that plain git knows nothing about.

On the website

README github
A file named README.md at the repo root. GitHub renders it automatically on the repo’s front page, making it the first thing any visitor reads.
Markdown .md github
The plain-text formatting syntax READMEs are written in: # for headings, **bold**, -  for bullets.
visibility github
Whether a repo is public (anyone on the internet can read it) or private (only you and people you invite). Changeable later, but anything pushed while public may already have been copied.
